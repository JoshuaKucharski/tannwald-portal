# ADR-012: Deploy nativ auf geteiltem nginx/php-fpm-Server

**Status:** angenommen · **Datum:** 2026-11-02 · **Quelle:** RunBook Phase 2, Aufgabe 4.1 (Wahrheit 5, D3, D4, D9,
D11 = Variante 2); Auftrag `tw2-7-server`, Nachträge 1–4 (Entscheid des Masters 2026-11-02 22:11)

## Kontext

Die Demo soll live unter `mytannwald.getleaven.com` laufen (D4). Geplant war ein eigener Hetzner-CPX31 mit Docker
Compose (Caddy, php-fpm, MariaDB, Mailpit, Ollama, Cron). Der Betreiber nimmt stattdessen seinen vorhandenen Server
91.98.229.15: Ubuntu 24.04.3, 2 vCPU, 3.7 GB RAM (2.6 GB frei), nginx 1.24 mit fünf produktiven Sites, MySQL 8.0.46,
PHP 8.3.27-fpm aus dem ondrej/php-PPA, certbot 2.9, ufw, fail2ban, **kein Docker**. Das Projekt läuft lokal mit
PHP 8.4 und MariaDB 11.4; `composer.lock` sperrt `symfony/cache` 8.0 (verlangt PHP ≥ 8.4).

## Entscheid

Das Portal läuft **nativ** neben den anderen Sites, nach deren Muster, und fasst nichts Fremdes an:

- **nginx-Vhost** `mytannwald.getleaven.com` + `mail.mytannwald.getleaven.com` aus Vorlagen (`deploy/nginx/`): erst
  eine HTTP-Fassung (für certbot), mit Zertifikat die TLS-Fassung wie bei firstbiodent.de; Drupal-Regeln nach dem
  offiziellen nginx-Rezept plus Sperrliste aus `web/.htaccess` (Snippet). Aktiv nur nach `nginx -t`, dann `reload`.
- **Zertifikat** über `certbot certonly --nginx` (zuerst `--test-cert`, Staging), `--deploy-hook 'systemctl reload
  nginx'` — certbot ändert unseren Vhost nicht, darum bleibt er idempotent aus der Vorlage erzeugbar; acme.sh bleibt
  unberührt.
- **PHP 8.4 neben 8.3** (Pakete aus dem vorhandenen PPA), eigener Pool `mytannwald` (Nutzer `tannwald`,
  `pm = ondemand`, höchstens 4 Prozesse à 256 MB, `open_basedir`), Socket `/run/php/php8.4-fpm-mytannwald.sock`.
  `/usr/bin/php` bleibt 8.3: verschiebt die Paket-Installation die Alternative, stellt `bootstrap.sh` genau den
  vorherigen Pfad wieder her. drush, composer und Cron finden PHP 8.4 über `/var/lib/tannwald/bin/php` vorn im PATH
  (drush startet seine Unterprozesse über `env php`).
- **MySQL 8.0** der Maschine: Datenbank und Nutzer `mytannwald`, angelegt über den root-Socket nur, wenn sie fehlen.
  `site:install --existing-config`, FULLTEXT (`ALTER TABLE` aus `hook_install`) und der Seeder sind auf MySQL 8.0.46
  mit dem `sql_mode` des Servers belegt (Generalprobe 4.1).
- **Ollama** als systemd-Dienst nur mit `bge-m3` (CPU, `127.0.0.1:11434`, `OLLAMA_KEEP_ALIVE=5m`), **Mailpit** als
  Binary-Dienst (`127.0.0.1:8025/1025`, UI hinter Basic-Auth), **Cron** als systemd-Timer (alle 5 min `drush cron`,
  dann `queue:run tannwald_embed` und `tannwald_summarize`). Jede Mail geht an Mailpit (Core-`php_mail` über
  `sendmail_path`, symfony_mailer über einen SMTP-Override), nie an den Mailserver der Maschine.
- **Werte** nur in `/etc/mytannwald/env` (640, root:tannwald; Vorlage `deploy/.env.example`); der Pool bekommt sie als
  `env[…]`, drush und Cron lesen die Datei im Kind-Prozess. `web/sites/default/settings.php` erkennt den Server an
  `TANNWALD_DEPLOY=1` und liest nur Namen. `reverse_proxy` bleibt aus (nginx spricht FastCGI; REMOTE_ADDR ist der
  Client — gefälschtes `X-Forwarded-For` belegt ignoriert).
- **Der Demo-Server ist kein Produktivbetrieb:** Demo-Konten mit dem Passwort `demo` sind gewollt. Der Seeder läuft
  dort nur mit dem ausdrücklichen Opt-in `TANNWALD_DEMO=1`, das ausschliesslich `deploy.sh` beim Seeder-Aufruf setzt;
  `TANNWALD_DEPLOY` allein erlaubt ihn nicht.
- **Skripte:** `deploy/bootstrap.sh` (einmalig/wiederholbar als root: Nutzer, Ordner, env-Datei, PHP 8.4, Pool, MySQL,
  Mailpit, Ollama, Units, nginx; `--tls`, `--dry`, `--render`) und `deploy/deploy.sh` (composer `--no-dev`, erstmals
  `site:install` + admin-Passwort aus der Umgebung + Seeder `--skip-summaries`, sonst updatedb → locale → `drush
  deploy`, Proben; zweiter Lauf „nichts zu tun“). Beide halten beim ersten Fehler, bauen geänderte Konfiguration bei
  rotem Test zurück und geben nie Werte aus. Der Code kommt per rsync (4.2, `tannwald-run.sh --deploy`).

## Begründung

Docker auf einer geteilten Produktionsmaschine mit 3.7 GB RAM und fünf fremden Sites wäre ein zweiter Netzwerk- und
Firewall-Stack (Docker umgeht ufw), zusätzlicher Speicher und ein Betriebsrisiko für Sites, die nicht uns gehören.
Nativ nutzt das Portal, was die Maschine schon betreibt (nginx, MySQL, certbot), und bringt nur mit, was fehlt
(PHP 8.4, Ollama, Mailpit) — jeweils als eigener Dienst mit eigenem Nutzer, Socket und Port auf 127.0.0.1.

## Konsequenzen

- RAM-Spitze (Generalprobe): bge-m3 geladen 1244 MB, php-fpm 4 Kinder zusammen 149 MB, drush 72–103 MB → etwa 1.6 GB
  von 2.6 GB frei; Ollama entlädt das Modell nach 5 min Leerlauf.
- Embeddings auf 2 vCPU sind langsam: bge-m3 ohne GPU auf dem M1 0.49 s je Chunk; der erste Seeder-Lauf (575 Chunks)
  dauert auf dem Server geschätzt 10–20 min.
- Lokal (DDEV, MariaDB 11.4) und Server (MySQL 8.0) unterscheiden sich in der Datenbank; FULLTEXT und Install sind auf
  MySQL 8.0.46 belegt, ein Rückweg auf MariaDB ist nicht nötig.
- Verworfene Variante: Docker Compose (Caddy, php-fpm, MariaDB, Mailpit, Ollama, Cron) — zu einem Drittel gebaut
  (`docker compose config` und `caddy validate` grün), nie committet, nach dem Server-Befund verworfen.
- Kein Backup-SLA, kein Monitoring (RunBook §5); Backup-Nachtskript folgt in 4.3.

## Nachtrag 2026-11-02 (Aufgabe 4.2/4.3/4.5)

- **Deploy vom Mac:** `tannwald-run.sh --deploy` (Logik `deploy/remote.sh`) überträgt einen Export von `origin/dev`
  (`git archive`, nicht den geteilten Arbeitsbaum) per `rsync -rlptz --delete` mit `deploy/rsync-exclude.txt`; Abbruch
  bei ungepushten Commits auf `dev`. Danach `bootstrap.sh --tls` (nur wenn beide A-Records auf den Server zeigen) und
  `deploy.sh` über SSH (BatchMode, keine Wiederholung wegen fail2ban), Proben vom Mac, Vorher/Nachher-Messung der
  anderen Sites der Maschine. `--probe` liest nur, `--dry` zeigt die Pläne.
- **Besucher-Passwort (D9 a):** ein Paar `GUEST_USER`/`GUEST_PASSWORD` für Site und `mail.`; bootstrap erzeugt den
  apr1-Hash über stdin (gleiches Salz, solange das Passwort gleich bleibt). `/health` und `/robots.txt` (`Disallow: /`)
  ohne Passwort, `X-Robots-Tag: noindex` auf jeder Antwort.
- **Zertifikat:** `certbot certonly --nginx --dry-run` gegen die Test-CA, erst danach echt (Rate-Limit geschont).
- **Seeder** auf dem Server mit `--skip-queues`; die Embeddings (CPU, 10–20 min) und Zusammenfassungen (DashScope)
  holt der Cron-Timer. **Absender** `SITE_MAIL` (Override von `system.site:mail`). **Backup** nachts 03:30
  (`deploy/backup.sh`: mysqldump + files/ + private/, 7 Tage). **Chat** in `config/sync` auf `dashscope`.
