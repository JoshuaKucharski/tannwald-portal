# ADR-003: Vektoren im PoC in der Datenbank, produktiv OpenSearch

**Status:** angenommen · **Datum:** 2026-11-01 · **Quelle:** Pflichtenheft §15 (`docs/pflichtenheft.md`), Präzisierung
D6a des Betreibers (2026-11-01), umgesetzt in Aufgabe 3.1 (Modul `tannwald_ingest`), genutzt in 4.1–4.3 und 6.1

## Kontext

PoC „myTannwald“ (Kundenportal der Tannwald Verpackungstechnik AG), Lastenheft `docs/lastenheft.yaml`,
Pflichtenheft `docs/pflichtenheft.md`. Die Suche muss kapitelgenau treffen (Wireframe 02: Trefferzeile = Kapitel mit
Pfad), über Bedeutung finden („Folie reisst beim Siegeln“ → Kapitel 9.4 ohne gemeinsames Wort) und darf nur zeigen, was
das Konto sehen darf — dieselbe Schranke wie der Assistent. Produktiv stehen 2,5 Mio. Chunks an (Pflichtenheft §14);
im PoC sind es 581. Das Pflichtenheft sah Search API DB für den Keyword-Zweig vor; der Betreiber präzisierte mit D6a:
der Keyword-Zweig ist MariaDB-FULLTEXT in `DatabaseChunkStore::keyword()`, `search_api`, `search_api_db` und `facets`
werden nicht installiert, Facetten entstehen aus der Treffermenge (Wächter `ConfigSyncGuardTest`).

## Entscheid

Im PoC liegen Chunks und Embeddings in der Tabelle `tannwald_chunk` hinter einem `ChunkStoreInterface`
(`tannwald_ingest.chunk_store`): Keyword-Zweig über drei FULLTEXT-Indizes derselben Tabelle, Vektor-Zweig als Cosinus in
PHP über float32-Vektoren (`bge-m3`, 1'024 Dimensionen), beide mit Vorfilter über `access_keys` in SQL. Produktiv
übernimmt ein `OpenSearchChunkStore` hinter demselben Interface.

## Begründung

Unter 10'000 Chunks reicht PHP-Cosinus; ein `ChunkStoreInterface` hält den Wechsel offen; OpenSearch vereint Volltext
und Vektor und steht beim Kunden auf der Liste. D6a dazu: **eine** Tabelle, **eine** Zugriffsschranke für beide Zweige,
kapitelgenaue Treffer ohne Search-API-Datasource für Chunks, und die Naht zu OpenSearch („Hybrid-Query nativ“) bleibt
dieselbe — Konsumenten kennen nur das Interface.

## Konsequenzen (gemessen)

- **FULLTEXT statt Search API (D6a).** `keyword()` rechnet `MATCH(title) * 3 + MATCH(heading_path) * 2 + MATCH(text) * 1`
  im BOOLEAN MODE ohne Operatoren (ODER-Semantik; `+-<>()~*"@` werden entfernt, „E-4711“ wird „E 4711“ und trifft über
  `4711` die Störungstabelle). Die Indizes `ft_title`, `ft_heading`, `ft_text` legt `tannwald_ingest_ensure_fulltext()`
  per `ALTER TABLE` an (aus `hook_install()` und den Kernel-Tests; das Core-Schema kennt FULLTEXT nicht). MariaDB
  11.4.13: `innodb_ft_min_token_size` 3 („TB“, „E“, „an“ fallen weg, „200“ und „4711“ bleiben), InnoDB-Stoppwortliste
  englisch plus „und“, „der“/„die“ werden indexiert. **Kein Stemming:** „Folie reisst beim Siegeln“ findet im
  Keyword-Zweig nichts Passendes, der Vektor-Zweig findet 9.4 auf Rang 1 — genau der Demo-Moment TC-06. Facetten zählt
  `facetCounts()` mit einem `GROUP BY` je Dokument (nid, vid, langcode) über die sichtbaren Treffer.
- **Tabelle statt Vektor-DB.** Embeddings liegen als float32 Little Endian (4'096 Bytes) in `tannwald_chunk.embedding`
  (`VectorPack`, Längenprüfung); `similar()` filtert in SQL (`CONCAT(' ', access_keys, ' ') LIKE '% <key> %'`,
  OR-verknüpft, Keys als Platzhalter, Teilstrings treffen nicht) und rechnet den Cosinus in PHP, eine zweite Query lädt
  nur die Top-k-Zeilen. Gemessen (M1, DDEV): `keyword` 1–3 ms bei 28 Zeilen; `similar` 3 ms bei 28 Zeilen, 371 ms bei
  5'028 Zeilen; ab 5'000 Zeilen im Vorfilter schreibt der Store einen Watchdog-Hinweis. Demo-Stand nach dem Seeder:
  581 Chunks aus 34 Fassungen (31 Dokument- plus 3 Bulletin-Fassungen), Embedding aller Chunks 60 s; Retrieval beider
  Zweige plus Fusion im Median 81 ms über 60 Eval-Fragen; Suche-Seite und Live-Suche 118–120 ms.
- **Chunking.** Abschnitte entlang `h2`/`h3`, Ziel 350 Tokens, Überlappung 60 an Satzgrenzen, Tabellen atomar (auch
  über 350 Tokens, mit Warnung), Listen zeilenweise; `heading_path` mit Trenner ` › `, letztes Element = Anker
  `#kapitel-<HeadingSlug>`. Über die 31 Fixture-Dateien: Tokens min/median/max 53/156/469; 37 von 44 Folgepaaren mit
  Überlappung, die 7 ohne liegen an Tabellengrenzen. Das Pflichtenheft nennt als Vergleich ein 800-Token-Fenster;
  die Eval-Analyse (4.3) zeigt, dass die Fehlschläge an kurzen allgemeinen Sicherheitskapiteln (2.1) und an
  Typ-Verwechslungen liegen, nicht an der Chunk-Grösse — Tuning in 6.1 setzt darum am Sicherheits-Retrieval und am
  Maschinentyp an.
- **Sicherheitsnaht.** `access_keys` = `implode(' ', EntitlementService::getRealmsForNode($translation))` je
  indexierter, veröffentlichter Fassung — exakt die kombinierten Keys aus ADR-002. Beide Zweige filtern vor dem
  Ranking; leere Nutzer-Keys liefern nie Treffer; ohne Entitlement-Dienst entstehen Chunks mit leeren Keys
  (unsichtbar). Gegenprobe: Vorfilter in `similar()` entfernt → `ChunkStoreTest` rot (fremder Key im Ergebnis). Nach
  dem Store prüft der Retriever jeden Treffer zusätzlich mit `$node->access('view')`. Der Index folgt dem Workflow:
  nur `published`-Fassungen haben Chunks, Zurückweisen oder Depublizieren löscht sie (`WorkflowVisibilityTest`,
  TC-10).
- **Exportregeln ohne Reindex.** Eine Änderung der Exportregeln ändert nur Nutzer-Keys, nie Dokument-Keys — die
  Tabelle bleibt gültig, der Cache der Nutzer-Keys wird über Tags invalidiert.
- **OpenSearch-Naht.** Konsumenten (Retriever, Suche-Seite, Live-Suche, Evals) kennen nur `ChunkStoreInterface`
  (`replaceForRevision`, `deleteForNode`, `deleteForRevision`, `keyword`, `similar`, `facetCounts`) und die
  Treffer-Zeile `{id, nid, vid, langcode, chunk_index, heading_path, title, text, exportklasse, dokumenttyp_tid,
  maschinentyp_tids, score}`. Ein `OpenSearchChunkStore` ersetzt den Dienst (`access_keys` als `keyword`-Feld mit
  `terms`-Filter, `knn_vector` 1'024, BM25 mit Boosts 3/2/1, Facetten als Aggregation); Chunker, Embeddings, Queue und
  Retriever bleiben. Die Score-Skalen sind unvergleichbar (MATCH-Summe unbegrenzt, Cosinus 0.49–0.62 bei `bge-m3`),
  darum fusioniert der Retriever über Ränge (RRF), nicht über Scores — das gilt auch für OpenSearch.
- **Ollama ist geteilt.** Embedding und Chat laufen nacheinander: `queue-run` mit 28 Chunks dauert 5.9 s isoliert und
  56 s parallel zu Chat-Läufen; Seeder und Evals nie gleichzeitig mit dem Assistenten.

## Alternativen

- **Search API DB plus Facets (Pflichtenheft-Ursprung):** zweite Indexkopie der Chunks, zweite Zugriffsschranke
  (Search-API-Processor) neben `access_keys`, kein kapitelgenauer Treffer ohne eigene Datasource; durch D6a verworfen.
  Bleibt als Option, falls Facetten über Search API gewünscht werden (RunBook §5).
- **Vektor-Datenbank oder `pgvector`:** zusätzliche Infrastruktur für 581 Chunks; MariaDB hat keinen Vektor-Index in
  der eingesetzten Version; verworfen für den PoC.
- **OpenSearch schon im PoC:** zweiter Dienst in DDEV, Mapping, Analyzer und Sync-Logik in 48 Stunden; die Naht ist
  vorbereitet, der Nachweis für Phase 1 (Pflichtenheft §14, 5–8 PT).
