# ADR-013: Öffentliche Live-Demo ohne Besucher-Passwort

**Status:** vorgeschlagen · setzt Entscheid D9 des Betreibers um (2026-11-03 14:50: „Arbeitgeber sollen ohne Umstände sehen“);
den Text bestätigt der Betreiber in Teil 4 v2 der Anleitung (Zeile 4d.9) · **Datum:** 2026-11-03 · **Quelle:** RunBook
Phase 2, Aufgabe 4.5 (D9), Nachtrag 1 zum Auftrag 5.1; Berichte tw2-9 (E), tw2-11 (A), tw2-12 (B)

## Kontext

Die Demo unter `mytannwald.getleaven.com` richtet sich an Leser, die das Repo und die Site ohne Absprache ansehen sollen.
Aufgabe 4.5 hatte zwei Varianten vorgesehen: (a) Basic-Auth vor der ganzen Site mit einem Passwort, das der Betreiber
weitergibt; (b) Site offen mit stündlichem Reset per Cron. Die Demo-Konten tragen das Passwort `demo`, das im Repo und im
README steht; `admin` hat ein eigenes Passwort aus der Server-Umgebung.

## Entscheid

1. **Die Site ist offen** (`SITE_AUTH=off`): kein Besucher-Passwort, die Anmeldeseite zeigt die sieben Demo-Konten als Chips,
   ein „?“-Fenster erklärt die Demo, ein Button führt zum Repo. Der Kontowechsel geht über Abmelden und den nächsten Chip; die
   Demo-Leiste (masquerade) gibt es nur lokal (Split `dev`).
2. **Was offen ist, ist begrenzt:** Suchmaschinen bleiben draussen (`robots.txt` „Disallow: /“, `X-Robots-Tag: noindex` auf
   jeder Antwort); Passwort- und E-Mail-Felder der Demo-Konten sind im Nutzerformular gesperrt (niemand kann ein Demo-Konto
   übernehmen); `admin` ist kein Demo-Konto; der Assistent hat ein Monatslimit von 2'000'000 Tokens (Deckel CHF 1.60) und
   Flood-Schutz je Konto; Mails verlassen den Server nie (Mailpit); Mailpit selbst bleibt hinter dem Besucher-Passwort
   (`GUEST_USER`/`GUEST_PASSWORD`), ebenso wie bei `SITE_AUTH=on` die ganze Site.
3. **Kein stündlicher Reset:** Änderungen der Besucher (Lesebestätigungen, Freigaben, Support-Anfragen, Chat-Verlauf) bleiben,
   bis der Betreiber `tannwald:demo-reset` auslöst. Ein Reset-Timer wäre ein kleiner Zusatz in `deploy/systemd/` (Variante b),
   bewusst nicht gebaut, weil ein Reset mitten in einer Vorführung schlimmer ist als ein veränderter Demo-Stand.
4. **Zurück zur geschlossenen Site** ist eine Zeile: `SITE_AUTH=on` in `/etc/mytannwald/env` und `tannwald-run.sh --deploy`;
   die Probe erwartet dann 401 ohne Passwort.

## Konsequenzen

- Jeder kann Daten der Demo verändern; der Audit-Log und die Freigabe-Queue zeigen das. Vor einer Vorführung lohnt ein Blick
  auf `--deploy --probe` (Zählungen, Zusammenfassungen) und bei Bedarf ein Reset.
- Die Demo-Konten sind bewusst öffentlich; ein Leak-Test gegen ein öffentliches Konto bleibt aussagekräftig, weil die Rechte am
  Konto hängen, nicht an der Geheimhaltung des Passworts.
- Site und Mailpit teilen sich bei `SITE_AUTH=on` ein Passwort-Paar; ein eigenes Paar für die Site wäre ein kleiner Zusatz
  (Bericht tw2-7 §3 g), ohne Bedarf, solange die Site offen ist.
- Verworfen: Variante (a) als Standard (Hürde für Leser, Passwort müsste weitergegeben werden), Variante (b) stündlicher Reset
  (Vorführungen würden unterbrochen).
