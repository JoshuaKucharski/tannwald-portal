# ADR-007: Migrate API für Stammdaten

**Status:** angenommen (umgesetzt in 2.3, Modul `tannwald_demo`) · **Datum:** 2026-11-01 · **Quelle:** Pflichtenheft §15
(`docs/pflichtenheft.md`), §6.4, §7

## Kontext

PoC „myTannwald“ (Kundenportal der Tannwald Verpackungstechnik AG), Lastenheft `docs/lastenheft.yaml`,
Pflichtenheft `docs/pflichtenheft.md`. Firmen, Maschinen und Konten kommen produktiv aus SAP, Dokumente aus einer
Dokumentablage, Bulletins aus der Redaktion. Im PoC simulieren JSON- und HTML-Dateien unter `fixtures/` diese
Quellen. Die Demo muss sich jederzeit wiederherstellen lassen, ohne dass jemand Daten von Hand anlegt.

## Entscheid

Firmen, Maschinen, Konten, Dokumente und Bulletins kommen über die Migrate API aus den Fixtures, produktiv aus SAP.
Fünf Migrationen liegen als Plugins in `web/modules/custom/tannwald_demo/migrations/*.yml`, nicht als
Konfiguration:

| Migration | Quelle | Ziel | ID |
|---|---|---|---|
| `tannwald_firmen` | `sap/firmen.json` (`url` + `json`) | Term `firma` | `sap_nr` |
| `tannwald_maschinen` | `sap/maschinen.json` | Node `maschine` | `seriennummer` |
| `tannwald_users` | `sap/nutzer.json` | Nutzer (Passwort `demo`, gehasht) | `name` |
| `tannwald_dokumente` | `dokumente/manifest.json` (Parser `tannwald_document_versions`) | Node `dokument`, eine **Revision** je Version | `id` + `version` |
| `tannwald_bulletins` | `bulletins/manifest.json` | Node `bulletin` | `id` |

Die Dokumente nutzen eine eigene Destination `tannwald_document_revision`. Je Quellzeile (Manifest-ID, Version)
entsteht genau eine Revision in Manifest-Reihenfolge. Alle Sprachen einer Version sind Übersetzungen dieser einen
Revision und werden in einem einzigen Save geschrieben. Jede Übersetzung erhält `moderation_state = published`, die
Datei liegt unter `private://dokumente/<datei>`.

`drush tannwald:demo-install` führt die Migrationen mit `MigrateExecutable` aus (dazu Terme, Exportregeln, Rebuild
der Zugriffsrechte, Lesebestätigung und Queues). `drush tannwald:demo-reset` rollt sie zurück und spielt sie neu ein.

## Begründung

- **Idempotent und Delta:** `track_changes` vergleicht je Zeile einen Hash. Ein zweiter Lauf überspringt
  unveränderte Zeilen (gemessen: 0 Änderungen, 0.7 s); geänderte Zeilen werden an Ort und Stelle aktualisiert. Der
  Dokument-Parser nimmt die Prüfsumme der HTML-Dateien in den Hash auf. Ziele, die von Hand gelöscht wurden, markiert
  `demo-install` vor dem Import zur Neuübernahme.
- **Rollback:** Die Map-Tabellen kennen jedes Ziel. `demo-reset` löscht genau die Demo-Entities und lässt admin und
  andere Konten stehen.
- **Fixture und SAP teilen die Migration:** Produktiv ersetzt eine OData-URL (`urls`, Data-Fetcher `http`) die
  relativen Dateipfade, und `high_water_property` begrenzt auf das Delta. Process und Destination bleiben gleich.
  Die relativen Pfade löst `hook_migration_plugins_alter` gegen `DRUPAL_ROOT/../fixtures` auf (Einstellung
  `tannwald_demo_fixtures_path`).
- **Eigene Destination statt Importer-Dienst:** Die zweite erlaubte Variante, ein Dienst mit eigener
  Idempotenz-Tabelle, hätte Map, Hash, Rollback und Zählung nachgebaut. Die Destination nutzt die Map von Migrate
  (`lookupDestinationIds([id])` findet den Node einer Manifest-ID) und braucht nur `import()` und `rollback()`.
  Mehrere Sprachen je Save statt einer Revision je Sprache erzeugen keine doppelten Chunks: Ältere veröffentlichte
  Revisionen behalten in 3.1 ihre Chunks.

## Konsequenzen

- Die Revisionen eines Dokuments entsprechen den Manifest-Versionen (22 Revisionen, 31 Revision×Sprache bei
  20 Dokumenten). Eine Version ohne die Originalsprache des Nodes lässt die Zeile scheitern; diesen Fall gibt es in
  den Fixtures nicht.
- Der Rebuild der Zugriffsrechte nach dem Import ist Pflicht. `node_install()` schreibt eine Zeile, die allen alles
  zeigt; ohne Rebuild ist DemoInstallTest rot (Gegenprobe).
- `entity:user` behandelt `pass` als bereits gehasht; darum hasht das Process-Plugin `tannwald_password_hash`.
- Wer einen Nutzer löscht, löscht in Core auch dessen Nodes (`node_user_predelete`). `demo-reset` löscht
  Demo-Konten erst nach den Inhalten.
- Grenzen: `track_changes` erkennt geänderte Bulletin-HTML-Dateien nicht, nur geänderte Manifest-Zeilen; abhilft
  `demo-reset`. Migrationen hängen über `migration_lookup` voneinander ab; ändert sich eine Firma, werden ihre
  Maschinen nicht neu geschrieben, die Referenz bleibt aber gültig.
- Ausbau: Für die produktive Variante braucht es OData-Fetcher, Authentifizierung über das `key`-Modul,
  `high_water_property` und einen Cron-Lauf statt Drush — siehe Pflichtenheft §14.
